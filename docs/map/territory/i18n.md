# i18n

## What it is

Putting every user-facing string in the user's language. Each package has its own dictionary and its own `t()`, and the supported locales are a closed `Locale` type — `ko-KR` and `en-US` — defined separately in each package.

## Governing decisions

**None.**

## Design model

- Lookup order: an override from `TranslationOverrides` for that key and locale, then the package dictionary, then the key itself. A missing key renders as its own name.
- The two `t()` functions differ: subscription's takes a fourth `params` argument and replaces the first `{name}` occurrence of each param; auth's has no params.
- `TranslationKey` is exported but `t()` accepts any string, so a typo compiles.
- Every auth component takes a `translations` prop; no subscription component does.
- `Locale` and `TranslationOverrides` are declared once per package. They are identical today, and nothing makes them stay identical.
- Adding a language touches both dictionaries, both `Locale` types, and the terms markdown.

## Code

- `packages/auth/src/i18n/index.ts` — `t`, `TranslationKey`, `dict`

## Blast radius

- [terms-content](terms-content.md) — terms are keyed by `Locale`; a new locale needs its markdown files.
- [login](login.md), [terms-agreement-ui](terms-agreement-ui.md), [account-screens](account-screens.md) — auth keys; renaming a key silently renders the key name.
- [login](login.md) — `LoginView`'s error fallback detects missing text by `t()` returning the key itself; changing that fallback breaks it.
- [pricing-ui](pricing-ui.md), [subscription-status-ui](subscription-status-ui.md), [checkout](checkout.md) — subscription keys, and the `{param}` substitution they rely on.
- [plan-catalogue](plan-catalogue.md) — every entitled app id needs an `app.<id>` key.

## Known holes / open

- Several user-facing strings bypass `t()`: inline `ko ? … : …` ternaries in `PricingView` and `SubscriptionView`, and `useCheckout`'s English error messages.
